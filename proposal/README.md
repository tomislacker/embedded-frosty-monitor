# FrostSight proposal package — internal notes

This directory holds the customer-facing sales/proposal package for
FrostSight (working name), the diagnostic/monitoring service built on the
frosty-monitor hardware. Everything in here is meant to be printed to PDF
and sent to prospects or handed to on-site staff. This README itself is
internal only — never send it to a customer.

## What each file is

| File | Audience | Purpose | Printed length |
|---|---|---|---|
| `exec-summary.html` | Owner-operator, first contact | One-page teaser: the problem, what we do, pricing at a glance, call to action | 1 page |
| `service-proposal.html` | Owner-operator (primary) + distributors (partner section) | The full proposal: economics, methodology, engagement lifecycle, pricing, safety/data summary, FAQ, signature block | 6 pages (cover + 5 content pages) |
| `data-handling.html` | Any customer asking "what happens to my data" | What's collected, what isn't, where it lives, who owns it, retention | 1 page |
| `staff-sheet.html` | On-site staff at the machine | Laminated placard: press the button if something's weird | 1 page |

Two files referenced from `service-proposal.html` are **owned by other
tooling**, not by this package, and are not created here:

- `sample-diagnostic-report.html` — an example of the written report a
  customer receives after a Diagnostic Deployment. Generated by the
  analysis pipeline from real (or representative) deployment data.
- `failure-signatures.html` — the reference gallery of what common failure
  modes look like in the sensor data. Also generated by the analysis
  tooling.

Both are linked by relative path from `service-proposal.html`
(`sample-diagnostic-report.html`, `failure-signatures.html`). If you're
sending the proposal before those files exist in this directory, either
wait for them or strip the links — don't ship a proposal with dead links.

## How to print to PDF

Each HTML file is fully self-contained (inline CSS, no external assets or
CDNs) and already styled for print: US Letter, ~0.75in margins via
`@page`/`@media print`, page breaks kept out of the middle of tables and
callout boxes.

1. Open the file directly in a browser (Chrome/Chromium recommended —
   these were built and checked against it).
2. Print (Ctrl/Cmd+P) → destination **Save as PDF**.
3. Margins: **Default** (the page already sets its own via `@page`; don't
   also select "None" or "Minimum" in the print dialog, or the layout will
   sit too close to the paper edge).
4. Background graphics: turn **on** ("More settings" → "Background
   graphics" in Chrome) — several elements (the accent-colored callouts,
   pricing table headers, the "YOUR JOB" box on the staff sheet) rely on
   background color to read correctly.
5. Headers/footers: turn **off** the browser's own header/footer — each
   doc already has its own footer line built in.

Verified page counts (Chromium headless, `--print-to-pdf`, default
margins): exec-summary 1p, service-proposal 6p (cover + 5), data-handling
1p, staff-sheet 1p.

## What to customize before sending

Every doc carries a `DRAFT v0.1` tag in the footer and the pricing is
explicitly marked draft — that's intentional and should stay until pricing
is actually confirmed. Beyond that, fill in before sending:

- **`service-proposal.html` cover page** — replace `[CUSTOMER / SITE NAME]`,
  `[DATE]`, and `[MACHINE MODEL(S) / COUNT]` in the "prepared for" block.
- **`data-handling.html` contact line** — replace `[CONTACT EMAIL]` and
  `[CONTACT PHONE]` with real contact details.
- **Cross-links** — confirm `sample-diagnostic-report.html` and
  `failure-signatures.html` exist alongside these files before sending the
  proposal; the links are relative and will 404 as local files otherwise.
- **Pricing** — once DRAFT pricing is confirmed, update the `DRAFT v0.1`
  footer tag on all four files to the confirmed version, and drop or reword
  the "pricing subject to confirmation" footer language if it's no longer
  accurate.
- **Staff sheet QR box** — the QR code is a placeholder (dashed box labeled
  "QR code here"). Replace with the actual QR image before printing and
  laminating; there is currently no generated QR code anywhere in this
  package.
- **"FrostSight (working name)"** — once the name is finalized, decide
  whether to update the footer tag across all files or keep "working name"
  until a formal rebrand/launch.

## Notes on scope

This package covers the primary audience (bar/restaurant owner-operators
with 1–5 machines) and the secondary audience (distributors/service
companies) via a dedicated partner-program section inside
`service-proposal.html` — there is no separate distributor-only document by
design.
